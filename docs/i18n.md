# Localization

## Architecture and current status

Use **Android resources at runtime, Weblate for translation management, and a
replaceable machine-translation provider for generating drafts**. There is no
custom dictionary, runtime translation engine, network permission, model download
or fixed language enum. The checked-in catalog currently contains English only;
Weblate hosting, provider configuration and additional translations are not yet
provisioned. This document is the setup recipe, not a claim that a service is live.

- `res/values/strings.xml` is the English source, keyed by stable semantic names.
- Translations are ordinary `res/values-<locale>/strings.xml` files. Android
  qualifiers support language, region and script, e.g. `values-fr`,
  `values-pt-rBR`, `values-b+zh+Hant`. These are examples, not an allowlist.
- AGP generates `LocaleConfig` from resources. Its locale filter is derived from
  the app's catalogs so Material/AppCompat translations alone do not advertise
  unsupported app languages. Adding a catalog requires no Java or language-list
  edit. Keep catalogs in locale-only folders; theme/layout resources belong in
  separate files.
- Android chooses the locale, plural forms and fallback. **Settings → App
  language** opens Android's per-app language settings (Android 13+). The initial
  choice follows the system. Missing translations fall back to English; the
  release checks require complete catalogs rather than knowingly shipping gaps.
- RTL is enabled, row indentation uses start/end, and interpolated app/profile
  names are bidi-isolated for display. Names, package IDs, shortcut formats and
  pinned labels are never rewritten when the language changes.
- Reboot progress uses stable state tags and existing counts, rendered in the
  current locale. Existing historical reports and root/helper exception details
  remain verbatim under localized labels. Shell output, protocol fields, log
  messages and exported diagnostics intentionally remain technical English.

This is portable: another Android project or translation tool can consume the
XML directly. Replacing the translation model or Weblate changes neither the APK
runtime nor the resource format. Existing translations remain usable if the
service disappears.

## Why not translation-model split APKs?

Language splits contain **translated resources**, not a translator. Play/bundletool
can generate them from an AAB if distribution later needs them. They do not solve
translation quality, source-change tracking or correction ownership. For a
sideloaded root manager, one APK containing the small text catalogs is simpler:
no split installer, missing-language downloads or per-language release matrix.

Generate translations before release, commit the exact output, and build without
contacting a model. Bundling a model adds storage/RAM/latency and still has finite
language coverage. Translating a destructive confirmation on-device also makes
its exact meaning harder to reproduce and audit. Do not translate profiles, app
names or device data through a remote service.

There is no credible promise of every language from any single model. **No fixed
language list in code** means adding any Android-supported locale as data, not
pretending it is already translated. An operator still selects target locales and
a model whose coverage, license and quality fit them. Regional/script variants
need deliberate evaluation too.

## Weblate setup (no custom translation pipeline)

Use a maintained Weblate instance. Configure a component against the repository
that actually owns these files, using its normal reviewed contribution path.
Do not grant a translation service release/signing credentials or automatic
protected-branch/release access.

| Component setting | Value |
| --- | --- |
| File format | Android String Resource (`aresource`) |
| Source language | English (`en`) |
| File mask | `res/values-*/strings.xml` |
| Monolingual base language file | `res/values/strings.xml` |
| Template for new translations | Empty |
| Language creation | Allow new translations; no project language allowlist |

Weblate creates a new locale file through **Start new translation**; it does not
need a seed dictionary or a developer-maintained enum. Use Android-style language
codes for filenames, especially script/region variants. Add only actual target
locales, not copies of English advertised as translations.

Choose a provider in Weblate's **Translation services**, explicitly:

- **Self-hosted Ollama** (built-in in Weblate 5.15+): select its reachable API URL
  and an explicitly installed model. This keeps inference on your infrastructure
  and does not require a custom HTTP client in this repository. Open weights do
  not necessarily mean an open-source license; review the model's license,
  redistribution terms, language coverage and resource requirements first.
- **Self-hosted LibreTranslate**: a built-in provider suited to supported
  language pairs; it is not universal-language coverage.
- **Hosted LLM/MT provider**: use a supported Weblate provider if you explicitly
  accept sending source text/context to it and its cost/privacy terms. Keep keys
  in Weblate, never Git, the APK or pull-request jobs.

Set source-language selection to the component's English source. Supply a short
translator persona/style and glossary: a *profile* is an Android user container,
a *clone app* is one installed app instance in that container, *disable/freeze*,
*force stop*, *stop profile* and *restrict background activity* are distinct.
Preserve scope and data-loss warnings; do not euphemize **delete ALL app data**.
Preserve format arguments, literal tokens, URLs and Android API identifiers.

Use Weblate's built-in **Automatic translation** add-on rather than a bespoke
script. Configure these choices visibly:

| Setting | Safe initial choice | Explicit alternative |
| --- | --- | --- |
| Source | Machine translation, selected provider | Translation memory first, then chosen provider |
| Query | `state:empty` (new strings only) | Target `state:needs-editing` for source-change drafts |
| Mode | Add as suggestion | Add as translation for unattended drafts, still behind the release review gate |
| Existing corrections | Leave them alone | Regenerate selected strings only after deliberately selecting them |

Do not run an all-strings overwrite on every build. Weblate tracks source changes
and marks affected translations for attention; unchanged corrected strings should
not be regenerated. Source-change suggestions can be AI-generated too. Translation
memory and glossary reduce repeated work. Corrections can be made in Weblate or
by editing the same XML in a reviewed change—no application patch is needed.

There is **no dependency on volunteer translators** to produce the first pass.
AI can draft and help review. It cannot prove that a deletion warning is faithful:
a maintainer must own the decision to accept drafts, optionally using independent
model review and fluent-user feedback. For an unattended policy, choose it
explicitly and record that language's machine-translated status; passing lint is
not a semantic-quality certificate. Store model/version and review provenance in
the translation change description. Do not put AI generation in release builds.

Weblate review state alone is not a release gate: an unapproved translation can
still be present in XML. Only merge accepted, complete catalogs, with the checks
below, through the normal review path. Leave new/incomplete/stale translations
in the translation contribution until resolved. A source-text change needs review
of affected locales even if every key still exists.

## Resource authoring and validation

1. Keep resource keys stable when correcting wording so Weblate can track changes.
   Give different meanings different keys. Keep full sentences rather than
   concatenating translated words. Counts use Android `<plurals>`, not `count == 1`
   in Java; include the target language's required categories.
2. Use indexed format arguments (`%1$s`, `%2$d`) so translators can reorder them.
   IDs/serials are strings to preserve their exact digits; quantities are numbers.
   `xliff:g` and adjacent XML comments explain protected arguments/tokens.
3. Never translate `translatable="false"` entries: the product name, literal
   `DELETE` confirmation token and the existing saved-name examples. The dialog
   displays the exact token it compares, independent of language. Preserve
   `{id}`, `{name}`, `{clone}` inside shortcut-help strings. Do not translate
   shell commands or persist translated names as a migration.
4. Use Android XML escaping (`\'`, `\n`, XML entities). Keep runtime code on
   `getString`, `getQuantityString` or resource-ID widget overloads; no alternate
   JSON catalog or custom resource loader.

Run from the project root with the SDK/JDK variables in the main README:

```sh
python3 tests/check_package.py
python3 -m unittest discover -s tests/build_tests -v
python3 build.py --self-check
python3 build.py --lint
python3 build.py
```

- Native Android lint fails missing/extra translations, invalid/inconsistent
  format arguments and missing plural categories. Static checks protect literal
  resources, format tokens and common Java UI text sinks.
- Self-check runs the existing release tests and debug tests. Only debug builds
  enable Android-generated `en-XA` (expanded/accented text) and `ar-XB` (RTL).
  These are test locales, not maintained translations or release languages.
- `tests-i18n/LocalizationTest.java` exercises resource fallback, zero/one/many
  counts, pseudolocalized screens/dialogs/accessibility, exact confirmation input,
  verbatim names, RTL row placement, language-settings routing, localized reboot
  state and generated locale discovery without dependency-only languages.
- Test on a device with expanded/RTL text, long names, large fonts, landscape,
  TalkBack and an actual language switch/recreation before release. Host layout
  checks do not establish translation quality, OEM Settings behavior or rendering
  on every Android version.
